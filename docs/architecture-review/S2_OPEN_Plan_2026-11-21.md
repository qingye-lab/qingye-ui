## 一、要回答的问题

架构稿 G2b：在没有预先定义业务工具的通用界面上，路线 A（UI SDK 的 Agent Bridge）相对路线 C（读无障碍树、
用 Playwright 按角色和名称操作）有没有可复现的独有收益，接入代价是否可控。

架构稿的原话是"若无真实业务需求，则 BIZ 不得虚构，OPEN 只能做技术可行性研究，不宣称产品收益。"本方案照此执行。

## 二、已核实的前提（2026-11-21）

- `@ui-sdk/react`、`@ui-sdk/core` 最新为 `0.1.0-beta.13`（Beta），来源仓库为 `vercel-labs/ui`，要求 React 19 及以上。
  `@qingye_lab/ui` 要求 React `^19.2.0`，版本门槛满足。
- 随包文档写明：Bridge 只发现 UI SDK 自己的组件和用 `definePrimitive` 定义的组件，不会自动识别现有 React 组件。
  Qingye 组件基于 Base UI，所以要让 A 看到 Qingye 组件，必须给每个组件写一层 `definePrimitive` 适配。
- `definePrimitive` 支持受控状态（`controlled` + `sync` + `createChange`）：值由父组件持有，变更回调可以取消。
  这意味着"薄适配层、不另持状态"在文档层面可能成立，但是否会多出 DOM 节点、重复的可访问名称或第二套焦点，要实测。
- `@qingye_lab/ui` 5.5.0 尚未发布到 npm（最新为 5.4.0）。被测包用当前提交的 `pnpm pack` 产物，记录提交号与 SHA-256。

## 三、做法

### 位置与依赖

- 新建独立目录 `/Volumes/SUNSANG 1/Codex/qingye-agent-lab/`，自带 git，不在本仓库内，不改 `@qingye_lab/ui` 的任何文件。
- 依赖：Vite + React 19.2、`@qingye_lab/ui`（打包文件）、`@ui-sdk/react` 与 `@ui-sdk/core` 锁定 `0.1.0-beta.13`、Playwright。
  安装时加 `--ignore-scripts`。

### 一个被测页面，五个场景

页面只用 Qingye 组件和朴素组合，全部数据本地模拟，没有后端写入。

| 编号 | 场景 | 要看什么 |
|---|---|---|
| O1 | 两个区块各有一个名为"负责人"的 Select | 只凭通道输出能否唯一定位到指定那个 |
| O2 | Dialog 里的 Select（弹层在 Portal 中），再打开一个确认 AlertDialog | 多层弹层与 Portal 下能否找到并操作 |
| O3 | Combobox 的选项要输入后异步加载 | 只在搜索后才出现的选项能否选中，是否等到收敛 |
| O4 | 可增删的条目列表，每行一个"名称"Input | 填第 3 行、删第 2 行后，定位是否仍然指向正确的行 |
| O5 | 父组件拒绝某个取值（受控取消） | 通道会不会把被取消的变更报成成功 |

### 两条通道，同样的规矩

- **C**：Playwright，只用 `ariaSnapshot()` 的输出和 `getByRole(角色, 名称)` 定位。
- **A**：只给 Select、Combobox、Input 三个组件写薄适配层，Bridge 挂在页面上；驱动脚本只用 `snapshot`、`query`、`act` 的返回定位。
- 两条通道都不许用 test id、CSS 选择器或对页面结构的先验知识。断言的是"仅凭本通道的输出能否唯一定位并完成"。
- 最终状态从独立事实源回读：页面把 React 状态以只读方式暴露给测试，不从被测通道回读。

### 先做可行性探针，不通过就停

先只给 Select 写适配层，检查三件事：

1. 适配层是否不另持状态，值完全来自父组件。
2. 接入后无障碍树是否不变（对比接入前后的 `ariaSnapshot`）：不多出 group，不出现重复名称。
3. Qingye Select 原有的键盘与焦点行为是否不变。

任何一项不通过，即架构稿写明的停止条件（双状态、双焦点、公共 API 破坏）。那时结论就是"A 目前接不上 Qingye 组件"，
G2b 有了答案，O1–O5 只跑 C 作为基线，不再扩展 A。

### 记录的指标

每个场景 × 每条通道：PASS / FAIL / NOT_APPLICABLE，是否误报成功，调用次数，通道输出的字节数（只作为上下文开销的粗略代理，不等于 token）。
A 另记：适配层代码行数、对无障碍树的改动、键盘与焦点回归。

## 四、能得出和不能得出的结论

- 这一轮用脚本驱动，不接模型。它能回答可行性、接入代价和状态是否收敛，因此**能得出"A 不值得接"，但得不出"A 更好"**。
  厂商宣称的优势是效率（工具调用数、token），要验证得接真实模型跑，这一轮不做。
- 架构稿要求的五项共同阻断用例里，下列各项这一轮标 NOT_RUN：
  - 跨通道 R2 封堵、只读白名单、意图作用域：测的是后端和应用的权限，在模拟数据上跑只能证明夹具本身，G3 未涉及。
  - SSR / Hydration：被测页面是纯客户端。
  - 提交完成证明（后端持久化与读回）：没有后端。
- 覆盖到的只有两项：同源状态收敛的一部分（O5 受控取消，以及独立事实源回读），异步与生命周期的一部分（O3、O4）。

### 探针：通过，未触发停止条件

| 检查 | 结果 |
|---|---|
| 适配层不另持状态（接受、受控取消、取消后再接受、人手点击后 Bridge 跟随） | PASS |
| 无障碍树不变（三个状态下 `ariaSnapshot` 逐字节相同；三个适配层全开时整页也相同） | PASS |
| 键盘与焦点序列不变 | PASS |

必要处理一处：原语会覆盖触发器的 `data-slot`，适配层须写回 `select-trigger`，否则 Qingye 的样式钩子失效。

### 5 场景 × 2 通道

| 场景 | C | A | A 的情况 |
|---|---|---|---|
| O1 同名"负责人" | PASS | FAIL | 输出里两个同名项无区块信息；随包文档要求同名控件靠 ref 或 row 文本区分，未提供按区块限定的机制，页面在标签里加区分词即可通过 |
| O2 Dialog 内 Portal 弹层 | PASS | FAIL | Button、Dialog 触发器没有适配层，Bridge 看不见 |
| O3 异步选项 | PASS | PASS | 没有加载信号，靠轮询 query 等到选项出现 |
| O4 增删条目 | PASS | FAIL | "删除"按钮没有适配层 |
| O5 受控取消 | PASS | PASS | 只看 `ok` 会误报成功；核对 `values` 或重取 snapshot 不误报 |

O2、O4 的失败是覆盖范围造成的：本轮只适配了三个组件。它说明的是每个要被操作的组件都要一层适配，接入成本随组件数增长，不说明 A 做不到。
A 的 O1、O2、O4 由检查 snapshot 中有无可用目标判定。调用次数与输出字节两条通道互有高低，C 的字节数随取样时机小幅波动，且不接模型，不据此比较效率。

### 接入成本

三个适配层共 171 行（含两份基线用的 Plain 组件，未扣除）。

### G2b 倾向

技术上可接：薄适配层能接到 Qingye 组件上，不产生双状态、双焦点，也不改无障碍树。但 A 只看得到适配过的组件，
要覆盖通用界面就得给按钮、对话框等逐一写适配层，同名控件还要求页面写出区分词。
本轮数据能支持的是：没有任何场景里 A 做到了 C 做不到的事；A 的代价是每个要被操作的组件一层适配。
（C 5/5、A 2/5 的比分受本方案只适配三个组件的范围影响，不作为依据。）
主 agent 的倾向：**在拿到真实模型的效率数据之前，A 对 Qingye 没有可复现的独有收益，暂不接入。** 验证包报告只陈述事实，不作比较；这条倾向是本文件加的，是否定案由评审方裁决。

### 仍为 NOT_RUN

- 模型驱动下的效率（工具调用数、token）。
- 跨通道 R2 封堵、只读白名单、意图作用域（G3）。
- SSR / Hydration。
- 提交完成证明（后端持久化与读回）。

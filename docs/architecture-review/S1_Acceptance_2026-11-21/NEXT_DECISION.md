日期：2026-11-21。依据见同目录 `report.md` 与 `scorecard.csv`。
本文件只给建议。G1 的裁决由评审方作出；S2 去向、提交与原始日志的处置已于 2026-11-21 裁决，见第六节。

## 一、G1 建议：G1-NO-CHANGE

建议裁为 **G1-NO-CHANGE**（保持现有工具链，不增加新基础设施）。

依据：

1. D0 条件下已经贴近满分。排除有缺陷的 T29 后，D0 计入 38 次，通过 37 次。唯一一次失败出现在有指南的一侧
   （代理没有照指南的组合写，同时撞上一个已修的库缺陷），不能归因于缺少指南。
   再加一层接线（D0.5）在这批题上没有可改进的余量。
2. 现有包内指南的作用已经被 DN 对照看到：删掉指南后，T7 与 T23 出现可重复的下降。
   所以该保留的是已经随包发布的指南，而不是新建别的东西。
3. 计入的 177 次运行里，类型检查报错、越界改文件、新增依赖都是 0。没有哪一类失败是"缺一个 CLI 或 MCP 才能避免"的。
4. 架构稿对 G1 写明的失败动作就是"保留当前指南；不立 CLI/MCP"，与评审方 G1-NO-CHANGE 的含义一致。

**必须同时说明的保留意见：** 架构稿 G1 的原文标准是 D0.5 相对 D0 的改进，这个对比没有跑（NOT_RUN），
用户已裁决跳过。上面的建议是由"D0 已到顶"加"DN 对照"推出来的，不是由 D0.5 实测得出的。
如果评审方认为 G1 必须以 D0.5 的实测为准，那么合乎事实的标签是 **G1-NEED-MORE-DATA**，补样范围见第三节。

为什么不建议另外两个标签：

- G1-PASS 的动作是"把有效的规范和少量文档修复合入"。这些修复已经先行合入 main 并把版本号升到 5.5.0（尚未发布到 npm，见 `report.md` 第七节第 7 条），
  没有待合入的内容；而且 D0.5 的改进没有实测，不满足"通过"的字面条件。
- G1-FAIL 的动作是"修文档或检查器，再做针对性复测"。S1 暴露的文档冲突（T29）和库缺陷（T1）已经修了，
  剩下的只是"修后没有复测"。这一项可以并入第三节的可选补样，不构成整体失败。

## 四、待用户决定：S2 放在哪里做，做不做

评审方的建议与本仓库已有的裁决不一致。我没有动手设计 S2-OPEN 的验证包，下面只列出走法并给一个建议，决定由用户作。

| | 评审方的建议 | 本仓库的裁决（`S0_Ruling_2026-11-20.md`） |
|---|---|---|
| 从哪里开始 | 先做 S2-OPEN，直接用本库现有组件和示例页面做技术对照 | 结论 2："S2（运行期 Agent 接入）不在本仓库做。本仓库不装 Vercel UI SDK，不做隔离实验，不写 Agent Adapter" |
| 启动条件 | G1 通过或确认无须改造后，优先设计 S2-OPEN 的独立验证包 | 第六节：在消费项目（候选 `demo/qingye`）有明确的运行期 Agent 需求、并同意安全门槛之后才启动；目前缺真实需求 |
| 共同点 | 不改 `@qingye_lab/ui` 生产组件，不引入新的 Agent 编排平台 | 同左 |

三种走法：

1. **维持原裁决。** S2 等消费项目出现真实需求再启动，现在不做。代价是评审方的 S2-OPEN 对照（Base UI 加 ARIA/Playwright，对比 Vercel UI SDK Agent Bridge）暂时没有数据。
2. **在本仓库之外建独立验证包。** 新建一个单独的目录或仓库，只把 `@qingye_lab/ui` 5.5.0 的打包文件当依赖装进来（5.5.0 尚未发布到 npm），
   用已部署的文档站示例页当被操作对象。这样字面上不违反"不在本仓库做"，也满足评审方"独立验证包"的要求。
   需要用户修改原裁决第六节的启动条件，因为 S2-OPEN 是技术对照，不依赖某个业务需求。
3. **在本仓库内用隔离的工作树做。** 这与结论 2 直接冲突，需要用户明确推翻该结论。

我的建议是走法 2，前提是用户确实想要 S2-OPEN 的数据；如果眼下没有运行期 Agent 的打算，走法 1 成本最低。
无论选哪一种，S2-BIZ 都应该等一个真实使用本库的 React 项目，这一点评审方与原裁决没有分歧。

### 1. S2：维持原裁决（第四节走法 1）

S2 现在不做，启动条件仍以 `S0_Ruling_2026-11-20.md` 第六节为准：消费项目出现明确的运行期 Agent 需求，
并且同意相应的安全门槛之后，才在那个项目里启动。

依据：

- 原裁决的启动条件是"有真实需求"。从 2026-11-20 确认至今，没有出现新的需求，也没有新的事实推翻它。
  走法 2 需要修改用户前一天刚确认的启动条件，缺少改动的理由。

  组件本身不发起隐式网络请求。这两条继续由本库的测试和审查守住，不需要单独的验证包。
- S2-BIZ 要等一个真实使用本库的 React 项目，这一点评审方与原裁决一致，不受本条影响。

需要改走法 2 时，前提是先由用户修改原裁决第六节的启动条件；验证包放在本仓库之外，只把已发布的包当依赖。

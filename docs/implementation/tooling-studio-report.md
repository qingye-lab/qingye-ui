## Implemented behavior

The tool package exposes `qingye-ui info/docs/check/init/theme/impact/report` and one shared ESM core. Explicit project configuration and theme schemas are implemented. Project package resolution supplies the actual installed version/catalog, with no network lookup. Legacy CSS is read-only and produces exact migration candidates alongside retained unmanaged evidence. Source/CSS/config fingerprints guard theme updates; files are atomically replaced, generated failures restore an existing source or remove only this operation's newly created source. Normalized paths and physical aliases cannot point source and generated CSS at the same target.

Consumer diagnostics use TypeScript AST/checker and PostCSS AST. The paint extractor is the shared AST owner migrated from the library test helper. Root changed the library test helper to re-export this same implementation; UI runtime does not depend on tooling. Actual named imports, aliases and reexports are resolved; arbitrary colors, undefined tokens, visual type/radius/motion literals and brand/brightness axis reuse are diagnosed. Native structural elements/layout/data values and explicit adapter boundaries are preserved. Unknown expressions remain unknown. Exact old-issue baselines and evidence-scoped, dated exceptions have separate disposition, and are never enlarged. Report/gate execution modes and 0/1/2 exit semantics are implemented. Preset evidence/status remains unchanged: recommended makes visual findings warning severity, personal makes them error severity, and legacy recognizes old problems only through the exact explicit baseline; each has a real gate policy. Actual used Chart/DataTable bindings (including aliases/reexports/namespace use) require only their own catalog optional peers; missing peers are explicit failures and incomplete execution. Private subpaths are FAIL even before failed module resolution. Public-control bypass remains UNVERIFIED and absent authoritative deprecations are N/A; clean broad reports stay UNVERIFIED. `info` with no configuration still returns actual installed facts and a missing-config result without creating files. The CLI also preserves a null expected source fingerprint when another editor creates that file.

Studio's local service only accesses startup-registered project IDs and validates loopback Host, same-origin requests, a session nonce, JSON/request limits and source fingerprints. Two independent iframe documents use actual library components; light/dark and density are independent of document brand. Import/export, validated diff, apply/reset/reread, advanced registry fields, impact/data-slot ownership and current/multi-project reports share the tool core. Synthetic Azure/Amber fixtures exercise class and attribute modes. Their design is an integration fixture; final visual choice remains deferred.

Preview version/source metadata is explicit. Target installed version, catalog hash and source/style hash must match Studio's source before preview or Studio apply is enabled. The backend repeats this check before mutation. A build-emitted preview-source manifest supplies the actual built fingerprint, so later disk edits cannot falsely describe an older bundle as current. A same-version but changed source/catalog is not presented as the installed project's actual components.

## Material limitations and boundaries

The two-layer existing token ledger is the sole influence index. Only recorded cases can substantiate runtime effect; stale or absent observations do not imply no influence. Studio component previews are restricted to the version/catalog/source fingerprint of the actual built manifest; mismatch disables Studio apply, while CLI edits remain separate explicit source operations. This implementation does not run regression browsers, parse arbitrary CSS bidirectionally, calculate an aesthetic score, infer risk semantics or provide speculative visual/behavioral autofix. Syntax-valid token values are not a contrast/cascade guarantee. Atomic replacements use optimistic concurrency and guarded rollback; cross-file consistency is checked on every read, not claimed as a global editor lock. Preset policy does not change factual status or manufacture an old-issue baseline; additional diagnostic rules require explicit authoritative evidence. Runtime layout, focus, accessible naming and business states remain separate browser/manual checks.
